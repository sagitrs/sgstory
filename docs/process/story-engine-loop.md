# 故事与引擎的协作循环：需求 → 能力 → 故事

## 这条循环解决什么问题

故事写在 `sagitrs/sgstory-books`，引擎在 `sagitrs/sgstory`。故事写到某处，常常需要引擎还不具备的能力。
过去这件事靠临时沟通：谁想到谁说，说完就做，做完没人验「故事里到底用上没有」。
本文把这条循环定成可追踪的五步：**需求进 issue、能力进 PR、验收回故事、用例常驻**。

## 角色

- 写作者（writer）：在故事里写。需要新能力时提需求；能力落地后在故事里真用上，并给出读数。
- 开发人员（developer）：把需求变成引擎能力（判据随件）；合入引擎主干。
- 测试（tester-3）：给出「能力可用」的验收形态；核两侧读数。
- 协调（coordinator）：分诊需求；维护需求台账；需求关闭时记账。

## 五个状态（每个需求都要走完）

### 1. 需求（写作者）

- 在 `sagitrs/sgstory` 开一条 issue，用模板 `.github/ISSUE_TEMPLATE/engine-capability.yml`；类型 label 取 `requirement`（项目内的"引擎能力需求"由本模板与台账区分）。
- 必填三样：
  1. **故事里的位置与意图**：哪一段、哪一句话、想做出什么效果；
  2. **今天的现状**：错误信息原文，或可观察到的行为（不要写「好像不行」）；
  3. **能不能用故事数据表达**：先答这一问（见下「先问数据」）；
- **必带能假样本**：一条故事侧用例（放 `cases/<slug>/`）或最小复现，**今天必须是红的**，能力落地后转绿。

### 2. 分诊（协调，当天）

判定三选一，写成 issue 评论：

- **引擎能力**：确实是引擎缺面，继续第 3 步；
- **数据可表达**：故事数据就能做到，退回写作者（不新增能力）；
- **已有能力**：能力已在，属用法问题，给指针（文档或既有用例）。

### 3. 实现（开发人员）

- 引擎 PR；正文写 `part of #<需求号>`；
- **判据随件**：那条能假样本必须在引擎侧可跑（或由故事侧用例承担），并写清「退化了会红在哪一格」；
- 合入引擎主干。

### 4. 验收（引擎侧功能级判据）

- **判据格**：该功能在引擎仓有自己的测试／判据格（能红能绿），随实现同笔落地；
- **不拿消费者当判据**：故事里用不用，不构成功能是否完成的判据；
- 完成后，写作者在故事里**采用**（下游动作，见第 5 步与台账的「采用情况」栏），需要新能力时**同笔 bump pin**。

### 5. 归档（协调）

- 需求 issue 关闭时写「验收读数」：谁、在哪条用例、什么读数；
- 更新需求台账（跟踪 issue，一张表：需求号、故事、状态、用例、落地 PR、pin）。

## 两条硬规矩

- **能假先行**：没有「今天必红的样本」，不进实现。样本可以是**引擎侧功能级测试**（首选），也可以是最小复现。
- **功能级测试才算完成**：引擎侧给的功能，必须带**功能级判据**（引擎自己的测试／判据格）才能算完成；
  **不把消费者（故事）当测试用** —— 故事用不用、怎么用，是下游的事，不该拿来当功能的验收。
  （故事侧读数仍可作旁证与留痕，但它是"采用情况"，不是"功能完成"的判据。）

## 先问数据

新增引擎能力之前，先回答「故事数据能不能表达」。

- 能用数据表达的，**不新增能力**（引擎侧增量概念数据化的既有裁定）；
- 必须新增的，说明「为什么数据表达不了」（自由度、跨故事复用、性能、还是引擎级约束）。

## 反模式（都已发生过，列在这里免得再犯）

- 故事侧先「绕过」缺能力（写成脚本、硬编码、注释标注），事后忘了补需求；
- 需求不带样本，实现完无法判「到底对不对」；
- 用了新能力却不 bump pin：线上会跑老引擎，新能力坏而发布照样绿；
- 只说「能力已可用」，没有故事侧读数：无法区分「能力好了」与「这个故事没用到」。

## 与规则仓票状态机的关系

本文件的五步是**项目视角**（谁在等谁、要验什么），不替代规则仓的票状态机（`gsvector-process` 的 `shared/issues.md` 是唯一权威源）。对应关系：

| 本文件 | 规则仓 | 执行者 | 证据 |
|---|---|---|---|
| 需求（提出） | 类型 label `requirement` | 写作者 | 票面（故事位置／现状原文／能假样本） |
| 分诊 | 仍开口 | 协调 | 分诊评论（引擎能力／数据可表达／已有能力） |
| 实现 | `status:working` | 开发人员 | PR 链接（`References #N`） |
| 验收 | `status:verifying` | 测试（引擎侧功能级判据） | 功能级测试读数；故事侧采用情况另记 |
| 归档 | 关闭 | 按规则仓转移表 | `[verified] <merge-commit> [env]` 或 `[done] <pr-url>` |

**注意（先备后用）**：规则仓要求「新状态的启用次序恒为 label 定义 → 审计脚本合法集 → 首次使用」。本仓类型 label（`requirement` 等）已有；`status:*` 的**审计合法集尚未建立**，所以现阶段只打类型 label，状态写在票面文字里；建齐之后再切到 `status:*`（另开跟踪票）。

## 验收读数集（能力落地时贴这几样）

贴在哪里：需求 issue 的验收评论。每一项都写「贴什么」与「什么输入能让它红」：

1. **功能级判据两向**：判据格从红转绿的读数 ＋ **把实现退回，则必须再红**（否则它没在判这件事）；
2. **pin 同笔**：books `.github/engine-ref.json` 的 ref 与新值，以及「bump 笔未夹带故事面」那道判据的读数；
3. **用例常驻**：`cases/<slug>/` 里那条用例 ＋ `case-run` 汇总行（绿／预期缺口／未归因 的条数）；
4. **发布面**：发布工作流那次 run 的结论（含用例门那一步）；
5. **故事侧采用（旁证）**：如果故事已经用上，贴一行玩家真会看到的原始输出（人读留痕用；**不进发布门硬格**）；
6. **归因链**：关票时写「谁、在哪条用例、什么读数」，并更新需求台账。

**两条「不通过」形态**：红得可归因（点名到格或行）／未判要出声（不许静默绿）。

## 第 4 步里哪些是机器代判的

- 「故事里真用上」则 由 `cases/**` 那条用例代判（发布门每次发布都会跑，红就不发）；
- 「pin 同笔」则 由发布工作流 §四4b 代判（bump 笔不得含 `stories/**`／`cases/**`）；
- 其余（哪一行输出、什么 DC、哪次骰）仍由人贴在验收评论里。

## 与其它机制的关系

- **用例驱动**（`#1262`）：能假样本就是本仓用例，落地后**常驻** `cases/`；
- **发布门**（`#1304`）：发布前跑全部用例，红就不发；因此故事的新能力在发布面是「可判的」；
- **声明件即权威**（`.github/engine-ref.json`）：pin 落后只告警不阻断，能力兼容性由发布门判；
- **判据台账**（`#1112`）：本循环产生的读数一并入册。

## 关于「新故事必须先带用例」

用过发布门就清楚：`case-run` 在「该故事 0 条用例」时判「过滤器未命中」（不给绿）。
这是**有意的**：新故事先带用例，才能被门保护。若将来确实需要「先发后补」，
那豁免**也要有对象**：带票号、带成立性判据、写进工作流注释，按既有下架口径办理。

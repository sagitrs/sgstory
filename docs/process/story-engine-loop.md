# 故事与引擎的协作循环：需求 → 能力 → 故事

## 这条循环解决什么问题

故事写在 `sagitrs/sgstory-books`，引擎在 `sagitrs/sgstory`。故事写到某处，常常需要引擎还不具备的能力。
过去这件事靠临时沟通：谁想到谁说，说完就做，做完没人验「故事里到底用上没有」。
本文把这条循环定成可追踪的五步：**需求进 issue、能力进 PR、验收回故事、用例常驻**。

## 角色

- 写作者（writer）：在故事里写。需要新能力时提需求；能力落地后在故事里真用上，并给出读数。
- 开发人员（developer）：把需求变成引擎能力（判据随件）；合入引擎主干。
- 测试（tester-3）：给出「能力可用」的验收形态；核两侧读数。
- 协调（coordinator）：分诊需求；维护需求台账；需求关闭时记账。

## 五个状态（每个需求都要走完）

### 1. 需求（写作者）

- 在 `sagitrs/sgstory` 开一条 issue，用模板 `.github/ISSUE_TEMPLATE/engine-capability.yml`；标签 `需求·引擎能力`。
- 必填三样：
  1. **故事里的位置与意图**：哪一段、哪一句话、想做出什么效果；
  2. **今天的现状**：错误信息原文，或可观察到的行为（不要写「好像不行」）；
  3. **能不能用故事数据表达**：先答这一问（见下「先问数据」）；
- **必带能假样本**：一条故事侧用例（放 `cases/<slug>/`）或最小复现，**今天必须是红的**，能力落地后转绿。

### 2. 分诊（协调，当天）

判定三选一，写成 issue 评论：

- **引擎能力**：确实是引擎缺面，继续第 3 步；
- **数据可表达**：故事数据就能做到，退回写作者（不新增能力）；
- **已有能力**：能力已在，属用法问题，给指针（文档或既有用例）。

### 3. 实现（开发人员）

- 引擎 PR；正文写 `part of #<需求号>`；
- **判据随件**：那条能假样本必须在引擎侧可跑（或由故事侧用例承担），并写清「退化了会红在哪一格」；
- 合入引擎主干。

### 4. 验收（写作者）

- 在故事里**真用上**（不是「能力可用了」，是「这一段现在这么写」）；
- **同笔 bump `.github/engine-ref.json`**（pin-aware：用了新能力就同笔升 pin，理由写进 `why`）；
- 读数：那条用例转绿，贴出读数（发布工作流会跑全部用例，见发布门）。

### 5. 归档（协调）

- 需求 issue 关闭时写「验收读数」：谁、在哪条用例、什么读数；
- 更新需求台账（跟踪 issue，一张表：需求号、故事、状态、用例、落地 PR、pin）。

## 两条硬规矩

- **能假先行**：没有「今天必红的样本」，不进实现。样本可以是故事侧用例，也可以是最小复现。
- **用上才算完成**：引擎 PR 合了不算完成；故事里用上并贴出读数才算。

## 先问数据

新增引擎能力之前，先回答「故事数据能不能表达」。

- 能用数据表达的，**不新增能力**（引擎侧增量概念数据化的既有裁定）；
- 必须新增的，说明「为什么数据表达不了」（自由度、跨故事复用、性能、还是引擎级约束）。

## 反模式（都已发生过，列在这里免得再犯）

- 故事侧先「绕过」缺能力（写成脚本、硬编码、注释标注），事后忘了补需求；
- 需求不带样本，实现完无法判「到底对不对」；
- 用了新能力却不 bump pin：线上会跑老引擎，新能力坏而发布照样绿；
- 只说「能力已可用」，没有故事侧读数：无法区分「能力好了」与「这个故事没用到」。

## 与其它机制的关系

- **用例驱动**（`#1262`）：能假样本就是本仓用例，落地后**常驻** `cases/`；
- **发布门**（`#1304`）：发布前跑全部用例，红就不发；因此故事的新能力在发布面是「可判的」；
- **声明件即权威**（`.github/engine-ref.json`）：pin 落后只告警不阻断，能力兼容性由发布门判；
- **判据台账**（`#1112`）：本循环产生的读数一并入册。

## 关于「新故事必须先带用例」

用过发布门就清楚：`case-run` 在「该故事 0 条用例」时判「过滤器未命中」（不给绿）。
这是**有意的**：新故事先带用例，才能被门保护。若将来确实需要「先发后补」，
那豁免**也要有对象**：带票号、带成立性判据、写进工作流注释，按既有下架口径办理。
